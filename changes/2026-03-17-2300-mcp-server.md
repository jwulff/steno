# MCP Server for AI Agents (PR #24)

## Why

The daemon was already persisting every session, segment, topic, and rolling
summary to SQLite, but nothing outside the TUI could read it. Claude Code,
Claude Desktop, and any other MCP-aware agent had no structured way to ask
"what did I work on yesterday?", "what topics came up in last week's
standups?", or "find the segment where we discussed the WAL mode decision."

The natural answer was an MCP stdio server that exposes the database via a
small set of read-only tools. The daemon stays the only writer; the MCP
server is a pure projection.

## How

Added a new Go module at `mcp/` (a sibling of `tui/` at the time —
PR #26 later consolidated both into `cmd/steno/`). It uses
`mark3labs/mcp-go` for the MCP protocol over stdio and `modernc.org/sqlite`
for pure-Go SQLite access (no CGo, matching the TUI's choice).

### Five tools

| Tool             | Purpose                                                                |
|------------------|------------------------------------------------------------------------|
| `get_overview`   | DB summary — total sessions, active session, recent sessions, date range |
| `list_sessions`  | Paginated session listing, filtered by status and time range            |
| `get_session`    | One session with all topics and the latest rolling summary              |
| `get_transcript` | Paginated segments with optional time-window filtering                  |
| `search`         | Cross-entity text search across segments, topics, and summaries          |

### Layering

```
mcp/main.go                 # stdio server setup + tool registration
└── internal/
    ├── db/                 # read-only SQLite store + models + testutil
    │   ├── store.go        # query layer (519 lines)
    │   ├── models.go       # Session, Segment, Topic, Summary
    │   └── testutil.go     # in-memory DB seeding for tests
    └── tools/              # one file per MCP tool
        ├── overview.go
        ├── sessions.go
        ├── transcript.go
        ├── search.go
        └── tools.go        # shared response shaping
```

The store opens SQLite with `mode=ro` + `_journal_mode=WAL` so it cleanly
shares the daemon's writer connection without blocking it.

## Key Decisions

- **Read-only by construction** — the MCP server opens the DB read-only and
  exposes no write tools. The daemon owns the schema; the MCP server is a
  pure projection. This means agents can't accidentally corrupt state, and
  the security review surface stays tiny.
- **Pure-Go SQLite (`modernc.org/sqlite`)** — same choice as the TUI. No
  CGo means the binary cross-compiles cleanly and ships without
  build-machine SQLite dependencies. The cost is slower writes, but this
  process never writes.
- **One file per tool** — each MCP tool gets its own `tools/<name>.go`.
  Easier to find, easier to test in isolation, easier for an agent reading
  the codebase to understand a single tool without pulling in unrelated
  query shapes.
- **`search` spans three entity types in one tool** — rather than separate
  `search_segments` / `search_topics` / `search_summaries`, one tool with
  scope flags. Agents reaching for "find X" don't have to guess which
  shelf to look on.
- **Stdio transport, not HTTP** — MCP stdio is the lowest-friction path
  for Claude Code and Claude Desktop integration: no port, no auth, no
  TLS. The daemon's Unix socket remains the only network surface.
- **Schema documented in `schema/README.md`** — both the daemon (writer)
  and the MCP server (reader) refer back to it. Schema is the contract;
  this PR also updated `schema/README.md` to reflect that the MCP server
  is now a documented consumer.

## What's Next

- **PR #26 will consolidate `mcp/` and `tui/` into one binary** — the
  separate module here was the right shape to land MCP in isolation, but
  two Go binaries doing closely-related work invite drift. Next PR makes
  `steno` one binary with a `--mcp` flag.
- Write tools (e.g. `tag_session`, `add_note`) — deliberately deferred
  until there's a real agent workflow that needs them. Adding writes
  changes the security story; landing read-only first lets agents prove
  out the surface before we open that door.
