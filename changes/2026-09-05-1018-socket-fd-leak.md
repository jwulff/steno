# Fix file descriptor leak in UnixSocketServer

Fixes #105.

## Why

The daemon can reach a state where it accepts socket connections and then never
answers them. The process stays alive, the LaunchAgent sees a healthy PID, the
socket file exists and accepts connections, and every client hangs on zero bytes
with nothing written to the log.

The cause is a descriptor leak. `removeConnection` unregistered a client's
wrapper from the connections map but never cancelled the underlying
`NWConnection`. Network.framework retains a started connection until it is
cancelled, so dropping the last Swift reference does not release the socket.
Every connection the daemon ever accepted stayed open for the life of the
process.

Measured against a running 0.5.2 daemon, 20 connect / status / close cycles:

```
fds on steno.sock before: 833
answered: 20 of 20
fds on steno.sock after:  854
```

One descriptor per connection, never released. That daemon had been up 86
minutes and was holding 941 open files, 909 of them dead unix sockets.

The wedge follows from there. Once the fd table is full, `accept()` fails with
EMFILE and `NWListener` stops calling `newConnectionHandler`. The client's
`connect()` still succeeds, because the kernel completes the unix socket
handshake into the listen backlog without the process participating, so the
client waits forever on a connection nobody will read. The unified log for the
wedged process carries 214 instances of `nw_network_agent_copy_struct
socket(AF_INET, SOCK_DGRAM, 0) failed [24: Too many open files]`, which is
Network.framework unable to open any socket at all.

Only the socket layer dies. Already open descriptors for SQLite and CoreAudio
are unaffected, so the engine keeps recording. In the reported incident it wrote
601 segments while every client hung.

## How

`removeConnection` now cancels the connection it removes, which is what actually
frees the descriptor. It looks the wrapper up rather than testing for existence,
so it can cancel what it removed, and the lookup doubles as the idempotency
guard for a connection that both fails a send and then reports EOF.

Send failures are the second route into the same leak: a client that dies
mid-response leaves a registered, un-cancelled socket behind. `CommandDispatcher`
and `EventBroadcaster` both swallow send errors by design, so the teardown has to
happen in the socket layer. `NWConnectionWrapper` now takes an `onSendFailure`
callback, wired by the server to `removeConnection`, and invokes it before
rethrowing.

## Key Decisions

**Cancel on EOF and error rather than adding a `stateUpdateHandler`.** The read
loop already sees both, since there is always a pending receive. A state handler
would be a second path to the same teardown for no additional coverage.

**Callback injection instead of a back reference to the server.** The wrapper
takes a `(UUID) -> Void` closure at init rather than holding the server, so there
is no retain cycle and the wrapper stays testable on its own. The parameter is
defaulted, so existing construction sites are unaffected.

**Idempotency in the map, not in a flag.** `removeValue` returning nil is the
signal that teardown already happened. No extra state to keep consistent.

**No watchdog in this PR.** The LaunchAgent plist has
`KeepAlive.SuccessfulExit=false` and no progress check, so a daemon that is alive
but deaf is still never restarted. That is worth having as defence in depth, but
it is a separate concern from the leak and belongs in its own change.

## Testing

Three new tests in `UnixSocketServerTests`, all failing before the fix:

- `closedConnectionsDoNotLeakDescriptors` reproduces the reported defect. Twenty
  raw-socket round trips against a real server, counting the process's open
  descriptors before and after. Growth was exactly 20 before the fix and 0 after.
- `clientDisconnectCancelsConnection` asserts the connection is left `.cancelled`
  rather than merely unregistered. Before the fix it sat in `.failed`, still
  holding its descriptor.
- `sendFailureNotifiesOwner` covers the send-failure teardown path.

Full suite: 711 tests, 0 failures (475 daemon, 193 Go, 43 app). The daemon
count drifts run to run because the Swift Testing teardown abort on macOS 26
truncates the tail of the pass stream, which is what the Makefile counts.

Two details worth recording for anyone extending these. The client has to
complete a full request/response round trip: a client that writes and closes
without reading is torn down by Network.framework before the read loop sees it,
and does not leak, so a fire-and-forget client silently fails to reproduce the
bug. And raw sockets rather than `NWConnection` on the client side, so the client
end is released synchronously on `close()` and any residual growth is
unambiguously the server's.

The `sendFailureNotifiesOwner` test cancels the connection before sending.
Pointing a connection at a socket nobody is listening on is not enough: the send
is queued against a connection that never becomes ready and the completion
handler is never called, which hangs the suite rather than failing it.

## What's Next

The two paths flagged as suspects in #105 are still open, and neither is the
cause of this wedge. `NWConnectionWrapper.send` has no timeout, and
`EventBroadcaster.broadcast` awaits each subscriber serially, so one stalled
client would stall every event behind it. Filed separately.

A heartbeat or last-progress timestamp in `status` would make this whole class of
failure externally detectable, independent of any individual cause.
